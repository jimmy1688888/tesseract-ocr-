## ⚠ 分階段 merge 與 GitHub 狀態不同步

決定是**累積完一個階段才一起併回 main**，不一張票併一次（memory：merge-in-stages-not-per-ticket）。
#1~#5、#23~#25、#27、#28 都維持 OPEN —— **那是刻意的**，併回 main 時 commit 裡的 `Closes #N` 會自動關票。
分支名 `fix/2-…` 其實是「這個階段」的分支，merge 前要不要改名屆時再定。

```bash
git log main..HEAD --oneline                                   # 這個階段累積了什麼
gh issue list --state open --json number,title --jq '.[] | "#\(.number) \(.title)"'
gh api repos/jimmy1688888/tesseract-ocr-/issues/18/dependencies/blocked_by --jq '[.[]|select(.state=="open")|.number]'
```

⚠ **pipeline.py 的檔案衝突**：#6、#7、#12~#15、#17、#18、#21、#30 都動 `pipeline.py`（#8~#10、#29 主要動
`employer_extract.py`）。那是檔案衝突不是
邏輯相依，沒連相依邊 —— 實務上一次只開一張。

**順序：線 A 結構票全部做完 → 線 B 加入 Gemini，比對後決定第二引擎採用 Gemini 還是 Vision（**二選一**，

（[TypeSafe System One / Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)）。在那之前不開票、不寫程式。

重新評估時的起點（2026-10-22 讀文章與對照程式的結論，未 grill）：
- **Jev 是什麼**：從「事先定義好的選項」裡挑一個，附校準過的信心；**不讀圖**（文章：not on images yet）、**不產生字串**。
  所以它取代不了 Tesseract 或 Vision，只能接在「從候選裡挑一個」的判斷上。早期存取階段（要排 waitlist），只能用 API
- **建議試點**：反查救援的名冊挑選。候選是有限的名冊條目，校準信心可以取代 0.72 門檻（ADR-0002），
  結果本來就標 manual_review。其次是雇主地址挑哪一行（#34 那類）、契約頁判定（#27 那類）
- **接點要先做深**：#13（救援回傳新列）→ 把「挑一家」切成獨立函式；雇主地址與契約頁要等 #8~#10。
  送審決策（`submission_decision.py`）已經可接
- **離線回測素材**：`employer_texts.json`（Vision 全文）不花 Vision 額度，可以直接重放（同 ADR-0008 先回測的原則）
- **風險**：① 個資（雇主姓名、地址、電話）送到第三方，要先確認規定允許；② 輸入與 Vision 同源，**不算獨立證據**，
  不能拿來湊「雙引擎一致 → 自動 key-in」，要寫 ADR、可能動 CONTEXT「獨立證據管道」；③ 服務還在早期，API 與價格可能變
