# Gemini 先只做離線比對,不進證據模型;走 Vertex 不走免費層

雇主欄位是整條 pipeline 唯一沒有第二證據的地方。許可證有多數票與雙引擎交叉,仲介機構
根本不做 OCR(查名冊),只有雇主 H~O 是「單一來源 + 疑慮標示」—— 而 `extract_employer_fields`
那 120 行 regex 的註解記了一整排版面性的敗因:兩欄序列化順序不可預測(32417、32508)、
傳真號混進電話(32447)、地號被 PHONE regex 誤當電話(32262)、契約標題頂上來當雇主名
(32508、32510)、紅章殘影把中文黏進英文地址行。

這些是**版面**的問題,而 regex 拿到的是已經攤平的文字。多模態模型看得到版面,所以
Gemini 在這裡的槓桿遠大於其他任何位置。

但它不能就這樣接進去。以下六個決定各自有被否決的替代方案。

## 一、只做離線比對,不進 pipeline

CONTEXT.md 的核心原則是「任何值要自動寫入,必須有兩個以上互相獨立的證據」,而
Gemini 進來是**第四條獨立證據管道**,既有的分派邏輯沒有位置給它 —— 它該當第二引擎
(與 Vision 交叉)?當第三票(進多數票)?還是取代 Vision?這三種接法的證據語意
完全不同,而在沒有量測之前,選哪一種都是猜。

更關鍵的是不對稱性:**LLM 最擅長的事,恰好就是產出安靜錯值。** 它幾乎不留空。
`extract_employer_fields` 之所以錨不到就回空並註記,理由寫在
[employer_extract.py](../../employer_extract.py) 的註解裡 —— 實測 7 份有 6 份會把仲介框
整組當成雇主填進去,「那是看起來完全合理的錯誤資料,人工審核看不出破綻,比留空
危險得多」。一個會填空格的引擎放進這個位置,風險方向與整套設計相反。

所以先量,不接。

### 明確否決:讓 Gemini 讀許可證

許可證是 4 位數、無檢查碼、是整條 pipeline 的主鍵。LLM 幻覺出的數字與真值形狀
完全相同,而這一欄已經有多數票與雙引擎兩條證據管道、提升空間本來就小。
**風險最大、報酬最小的位置。** 不碰。

## 二、真值只認 Sheets P 欄「已核」

`upload_log.csv` 看起來是現成的真值,但它從結構上不能用:

| 問題 | 事實 |
|---|---|
| 只記許可證 | 寫入欄位是 `[timestamp, source_docx, final_value, status, reason]`;H~O 八欄一格都沒有 |
| 記的是機器輸出 | `_append_upload_log` 在「成功寫入 Sheets 之後」追加,人事後在 Sheets 改了什麼永不回流 |
| 循環論證 | 它會在「Gemini 讀對、現有程式讀錯」的每一格判 Gemini 錯 —— 恰好是要找的那些格 |

程式碼自己早就承認這點:`load_known_permits_from_log` 的 docstring 叫它「**軟版**
已知清單」,而 `verify_vision_result` 的參數註解寫「`known_permits`:僅影響 rationale,
**不影響 `should_keyin`**」。它當初就沒被允許決定任何事。

改為:人審完一列,自己在 Sheets **P 欄**填日期或打勾;只讀腳本抓 P 欄非空的列
回寫 `data/ground_truth.csv`。程式只 append A~O,不會動 P 欄,零程式風險。

「已核」必須由人標,因為**人審後未改動的列與從未被看過的列內容完全一樣** ——
這個事實無法從資料推斷出來。

## 三、走 Vertex AI,不走 AI Studio 免費層

兩邊共用 `google-genai` SDK,程式碼差別只有 `Client()` 的初始化參數,所以這個決定
本身**改一行就能反轉**。唯一不可逆的是已經送出去的影像。

| | AI Studio 免費層 | Vertex AI |
|---|---|---|
| 影像用於改善 Google 產品 | **會** | 不會 |
| 認證 | 另一把 API key | 現有 `IDENTITY` |
| 配額 | Flash-Lite 約 15 RPM,不可調 | 專案配額,可申請調升 |
| 用量與 Vision 同一份帳單 | 否 | 是 |

送出去的是移工勞動契約:雇主姓名、身分證號、住址、電話,還有勞工的資料。這一條
就足以否決免費層。

認證是第二個理由。Vision 與 Sheets 都走 `IDENTITY.credentials()`,而
[ADR-0001 之後的那次重構](../../README.md)剛把認證收斂到共用套件 `gcp-identity`,
就是為了消除「到底是誰的身分在呼叫」這種歧義。多一把 API key 等於再岔一條路,
而且得回答「怎麼把它發給不打指令的使用者」—— 進版控就公開了,放環境變數就要每人
各持一把。

成本不是考量:離線實驗約 42 次呼叫,即使全用最貴的 Pro 也約 $0.3。**免費額度在
這個專案的價值趨近於零。**

### 一度規劃、隨即否決:prompt 試錯階段用 AI Studio 網頁

原本打算在 AI Studio 網頁上手貼去識別化的裁切圖調 prompt,理由是「不必寫腳本」。
腳本寫完之後這個理由就消失了 —— `gemini_bench.py run --mode text --only 32508`
一次只打一份文件的五個欄位,十秒內出報表,那就是迭代迴圈本身。

而 AI Studio 反而**自己製造成本**:它的免費層會把影像用於改善 Google 產品,所以每次
試都得先做去識別化;走 Vertex 完全沒有這個問題,連塗都不必塗。用一個要額外前置工作的
管道去省一個已經不存在的成本。不用。

## 四、雙模式跑,做診斷分解

處理順序是 裁切 → 去紅章 → Vision → regex 解析,其中有兩個可獨立替換的環節,
而它們的診斷意義完全不同:

| 模式 | 輸入 | 測到的是 | 成本 |
|---|---|---|---|
| 文字 | `scan_results/employer_texts.json`(已快取的 Vision 全文) | **解析**的錯 | 零 |
| 圖片 | `scan_results/employer_crops/` 23 張裁切圖 | **讀值**的錯 | 一張 < $0.001 |

既有痛點橫跨兩者,而**分在哪一邊只能實測、不能從症狀推**。32508 是個現成的例子:

| | |
|---|---|
| 圖上實際印的 | 呂詩偉(3 字) |
| Vision 全文裡的 | `呂偉` —— **「詩」根本不在文字裡** |
| 現有解析吐出的 | `呂偉` |

症狀看起來像解析錯(名字不完整),實際是**讀值**的錯 —— 解析器忠實地讀出了文字裡
僅有的東西。文字模式不可能救回這一格,只有圖片模式有機會。反過來,同一份的
`地址: ※中市北屯區…`(紅章把「臺」吃成 `※`)與「英文地址續行插在『電話:』與號碼
之間」也都是讀值/序列化的產物。

順帶一提,現有的字數音節數檢查**攔到了這一格**(`H:中文 2 字與英譯 3 音節不符`) ——
安全網有效,所以這格是「已知的空/疑慮」,不是安靜錯值。

分解的用途是決定改動規模:**若文字模式已接近真值,只需換掉 regex、保留 Vision** ——
那是個小得多、且不碰任何引擎的改動。只有圖片模式明顯更好時,才值得談換引擎。

## 五、輸出要來源依據,不要自評信心

要求 Gemini 逐欄並陳「值」與「我在哪一行的哪個標籤旁讀到的」。

理由是可驗證性:**依據可以拿回去比對原文,自評信心不能。** 如果 Gemini 說雇主名是
某三個字、依據是「甲方名稱:某某某」這一行,而那一行在 Vision 全文裡不存在,那格
就是它編的,當場抓到。LLM 的自評信心校準很差,實務上會給每一格 0.9 —— 包括它編的
那幾格。

這也與疑慮標示的既有規矩一致(見 [ADR-0003](0003-employer-address-doubt-flag.md)、
[ADR-0004](0004-employer-name-doubt.md)):「我在某個標籤後面讀到這幾個字」是事實,
「我有 85% 信心」是推斷,而疑慮標示只陳述事實。

## 六、驗收:準確率提升 **且** 零新增安靜錯值

兩條要同時成立,第二條是硬條件:

1. 逐欄準確率高於現有做法
2. 在現有程式**留空或掛疑慮標示**的格上,Gemini 不可以填入一個看似合理卻錯的值

只看第一條會系統性高估 Gemini:救回 8 格對的、同時把 2 格填成看似正常的錯值,
準確率漂亮上升,而那 2 格正是整套設計在防的東西。
[ADR-0003](0003-employer-address-doubt-flag.md) 的成本判斷是「誤報成本是人多睜大眼
看一格,漏報成本是錯的地址悄悄流到下游」—— 只看準確率與這個判斷反向。

違反第二條的欄位不得自動寫入,最多只能當疑慮標示的材料。

## 等值判準分欄不同

比對規則本身會安靜地說謊:太鬆會蓋掉 Gemini 的錯,太嚴會把它的對判成錯,而兩種
情況在報表上都只是一個數字。

| 欄位 | 判準 | 理由 |
|---|---|---|
| 地址 | 過 `fold_variants` 再比 | 臺/台、全半形、一段/1段 是寫法差異,不是錯 |
| 姓名 | **逐字嚴格,不折疊** | `fold_variants` 折 鍾→鐘,而兩者都是常見姓氏;折疊會蓋掉漢字錯讀,而 [ADR-0006](0006-employer-name-pledge-page-rescue.md) 說漢字正是引擎差距最大處 |
| 電話 | 只留數字比 | `-`、`(0)`、全形連字號是格式差異 |
| 英文欄 | 統一大小寫與標點再比 | 契約英譯無單一正確寫法 |

報表同時保留 真值／現有／Gemini **三欄原文**,讓判準自己可被抽查 —— 同
`matches.csv` 留 `scan_tier` 欄供觀測的做法。

## Consequences

- 新增 `gemini_bench.py`(離線,不被 `pipeline.py` import)、報表
  `scan_results/gemini_bench.csv`、回測集 `data/ground_truth.csv`。
  `requirements.txt` 加 `google-genai`。
- **需要人先做兩件事**:GCP 專案啟用 Vertex AI API 並給服務帳號
  `roles/aiplatform.user`;Sheets 手動加 P 欄標題「已核」。
- 回測集在 Gemini 這件事之外仍然有價值 —— 本專案目前**沒有任何回測集**,
  七份 ADR 的結論全靠當時手動核對的少量樣本。
- **跑新一批會沖掉離線重放的素材。** `_dump_employer_texts` 是
  `write_text(json.dumps(texts))`、而 `texts` 每次跑都是新的空 dict,所以
  `employer_texts.json` 是**整份覆蓋**不是 merge;`matches.csv` 同樣。目前那 21 份
  含了七份 ADR 記下的全部痛點案例,重跑一輪 Vision 才買得回來,故**跑新批之前要先
  備份這兩個檔**。(`employer_crops/` 是逐檔寫入,會累積,不受影響。)
  這與 `EMPLOYER_TEXT_PATH` 旁邊那段註解的意圖相反 —— 它說快取的目的正是讓離線重放
  變成常態,但寫入路徑沒有 merge。改成 merge 是另一件事,未在本 ADR 範圍內。
- 模型定為 Gemini 3.5 Flash-Lite(未來真上線會用的那個)。代價是它不佳時分不出
  「模型不夠力」或「路線不通」;緩解是**只把判錯的格重跑一次 Pro**,約十次呼叫。
- 尚未決定的是接法本身。若驗收通過,「Gemini 在證據模型裡算第幾條管道」要另寫 ADR,
  本 ADR 刻意不預設答案。

## 已知缺口:P 欄簽的是整列,不是每一格

「已核」是列級別的事實,而**真值為空的那些格有兩種成因分不出來** ——「契約上真的
沒有這一欄」與「我審這列時沒特別看這一格」。前者若 Gemini 填了值就是安靜錯值,
後者則不是。

這與 [ADR-0004](0004-employer-name-doubt.md) 記的那個缺口是同一個形狀:兩種空值成因
從資料上分不出來,所以不猜。實務影響最大的是 M 欄(英文地址)—— 契約英譯本來就常
整欄缺漏。

暫不處理,因為每格簽核的成本遠高於它擋掉的風險;但**驗收時若安靜錯值集中在真值為空
的格上,要先確認那些格的真值,不能直接判 Gemini 失格**。逐格簽核要等到這件事真的
咬人再談。
