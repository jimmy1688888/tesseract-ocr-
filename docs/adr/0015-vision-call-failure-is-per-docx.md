# Vision 呼叫失敗只影響那一份;身分或權限被拒才整批中止

Google Vision 有兩個呼叫點,錯誤模式剛好相反:許可證那條(`pipeline.vision_text`)API 回報錯誤時
回空字串、被判成「Vision 沒取到號」,重試用盡的 503 則沒人接、整批中止;雇主那條
(`employer_extract.vision_full_text`)不重試、一律 raise,再被三個呼叫端各自吞掉 —— 次頁的 503
變成「次頁沒有台仲電話」,切結書頁的 503 變成「救不回」。**沒問到**與**問了、答案是沒有**在
Sheets 上長得一模一樣,審查的人分不出該重跑還是該自己看圖。**決定:分類的原則是「換下一份會不會
一樣失敗」。會的(拿不到憑證、身分或權限被拒 403/401)是整批的事,照舊中止;不會的(重試用盡的
暫時性錯誤、這張圖本身被拒)是 Vision 呼叫失敗,只影響那一份,而且一定要寫在那一列上。**
(2026-10-30 grill V)

## 各呼叫端怎麼處理 Vision 呼叫失敗

| 呼叫端 | 處理 | 寫在哪 |
|---|---|---|
| 許可證 Vision 驗證 | 那一份進人工審查,B 欄留 Tesseract 候選值 | D 欄:`[送Vision原因] … ／ Vision 呼叫失敗,未驗證` |
| 契約頁(雇主擷取) | 擷取狀況新增第六種「契約頁 Vision 呼叫失敗」,H~O 未擷取,切結書頁備援不跑 | L 欄:`契約頁 Vision 呼叫失敗,未擷取` |
| 切結書頁備援 | 停,不換下一張頁再打 | L 欄另加 `H:切結書頁 Vision 呼叫失敗` |
| 次頁台仲區塊(反查救援) | 該份不救,同一份不再打 | D 欄接上 `；反查救援未完成:次頁 Vision 呼叫失敗` |

最後一列是 CONTEXT「反查救援」**救不回時不另外註明**的例外:那條規則講的是「救過、沒救回」,
這裡是根本沒救。

## 錯誤怎麼分

| 錯誤 | 重試 | 結果 |
|---|---|---|
| 503、429 額度、逾時、連線斷 | 是(4 次,起始 2 秒) | 用盡 → Vision 呼叫失敗 |
| `InvalidArgument`、回應裡的 `error.message` | 否(Google 已經回答了這張圖) | Vision 呼叫失敗 |
| `PermissionDenied` 403、`Unauthenticated` 401、拿不到憑證 | 否 | 往上拋,整批中止 |
| 其他例外(程式 bug) | 否 | 不攔,往上拋 |

分類與重試只在一處:`vision_reader.GoogleVisionReader`。它對呼叫端的契約只有兩種結果 ——
回傳字串(空字串 = 讀到了、沒有字),或 raise `VisionCallFailed`;絕不用空字串代表失敗。

## Considered Options

- **任何 Vision 錯誤都整批中止。** 否決:一份 docx 一列、彼此獨立,第 30 份遇到 503 不該把前
  29 份驗好的結果丟掉。沒驗證的值本來就不會自動寫入,單份降級不會寫錯值。
- **任何 Vision 錯誤都降級成單份。** 否決:403 時每一份都會失敗、重跑也沒用,讓它跑完只會把
  一個 GCP 設定問題偽裝成一整批的資料問題。正常情況下 preflight 的閘門會先擋下,這裡是最後一道。
- **單份降級,但不寫在列上(只記 log)。** 否決:就是今天的形狀。列上看不出是沒問到,審查的人
  不知道重跑也許就好。
- **Vision 整個掛掉時(連續 N 份失敗)提早停止送 Vision。** 暫不做:一批二三十份,最多多等幾分鐘,
  結果是對的。遇到再說。

## Consequences

- 雇主那三處第一次有重試;一份 docx 最壞多等 2+4+8 秒。
- 擷取狀況從五選一變六選一;「擷取失敗」專指 Vision 呼叫失敗以外的例外。
- 測試要能不睡就測「重試用盡」,所以 `with_retry` 的時間 seam(#21)排在這個行為改動之前。
