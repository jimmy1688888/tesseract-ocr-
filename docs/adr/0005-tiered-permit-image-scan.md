# 許可證掃圖分層:先掃 {2,5,6},拿不到多數票才擴掃

21 份契約跑一次要 **2 小時 51 分**,其中 **10308 秒(99.7%)** 花在步驟 2 的
Tesseract 許可證掃描 —— 掃了 134 張圖,平均每張 77 秒。雇主擷取(含契約頁評分
與 Vision)只用了 296 秒。要讓這條 pipeline 跑得動,唯一有意義的施力點就是
「少掃幾張圖」。

## 圖序是有結構的,不是隨機的

把每張圖的上緣送 Tesseract 看內容,前段順序是固定的:

```
image1   雜訊/空白(掃描雜頁,32509 這張直接是空的)
image2   契約頁                    ← 雇主欄位,21/21 都在這;mol ROI 也只有這張讀得到
image3   契約條文/次頁              ← 台仲反查用
image4   切結書第 1 頁              Surat Pernyataan Biaya dan Gaji
image5   切結書第 2 頁              ← 32503、32510 的許可證
image6   切結書第 3 頁              ← 32509 的切結書多一頁,許可證就落到這
image7   空白
```

**許可證印在切結書的最後一頁**(簽署方欄 `VI. Pihak yang menandatangani`),
而切結書長度 2~3 頁不定 —— 這就是命中會在 image5 或 image6 的原因。

實測 21 份的命中位置:

```
image5 → 9 份    image6 → 10 份    合計 19 份(另 2 份全無命中)
image2 → 0 份許可證,只有 2 筆低信心 mol(32523 conf 37、32529 conf 28)
image1 / image7 → 從未讀出任何東西
```

故 `TIER1_IMAGES = {2, 5, 6}`。

### 為什麼用絕對序號,不用「倒數第 N 張」

19 筆命中裡 17 筆在倒數第 2 張,看起來倒數更漂亮。但**尾端掛著數量不定的空白圖**
(32510 的 image6、32509 的 image7 都是空的),倒數會數到空白;穩定的是前段的
內容順序。這是資料看起來支持、實際上會反過來咬人的一組規則。

## 這個設計錯了不會錯值,只會慢

第一層拿不到 permit 多數票,就把其餘圖全部掃完 —— 輸入回到與全掃完全相同。
所以「用 21 份歸納出 {2,5,6}」這件事本身不構成正確性風險。

代價是它會**安靜地失效**:換一家仲介、切結書頁數變了,第一層每份槓龜、每份
擴掃,總時間比全掃更長,而結果欄位一格都沒變、log 以外看不出來。故
`matches.csv` 新增 `scan_tier` 欄(1/2),掃完在 log 印「第一層 N/M 份一次命中,
擴掃 K 份」。這欄不參與任何決策,它唯一的作用是讓規則過期這件事看得見。

## 擴掃條件:必須是 permit 多數票,兩種「看起來有值」都不算

`has_permit_vote()` 要求 `id_from_vote and id and id_conf > CONF_VOTE_MIN`。
刻意排除兩種情況,它們各自對應一個會讓分層出錯的坑:

**mol 命中不算。** mol 只證明這是契約頁,不是許可證的讀值。32523 與 32529 的
mol 信心是 37 與 28 —— 讓這種值擋掉擴掃,等於用雜訊決定要不要去找真正的許可證。

**`PERMIT_PARTIAL` 不算。** 「幾個設定各讀出不同的值、湊不出多數」的 row 是有
`r.id` 的,很容易被誤認為「讀到了」。但 `process_large_vs` 的規則A2 不會採用它,
反而會掉進規則B 並以 `no_vote_rescue` 把整份推去走**台仲反查救援**:

```
現況    image5 部分命中無多數(conf 40) + image4 乾淨多數票
        → 規則A2 命中 image4 → 直接 key-in

若讓 PARTIAL 擋掉擴掃
        → image4 那票根本不存在 → 規則A2 沒東西 → 規則B → conf 40 < 50
        → 走台仲反查,值被反查回推的許可證覆寫
```

一個湊不出多數的爛讀值會把整份文件推進反查,而 D 欄只會寫「permit部分命中無
多數」,看不出它其實是「還有幾張圖沒掃」。這是分層最危險的一條路徑。

## 台仲反查不受影響

反查走 `_agency_block_lines()` → `_scored_pages(docx_path)` → `_docx_images()`,
**自己從 zip 重讀全部圖、自己 Tesseract 評分挑契約頁**,再取下一張當次頁。
許可證掃描的圖片過濾碰不到它。雇主擷取同理。受影響的只有許可證那一欄。

觸發時機在上述條件收緊後與現況相同:沒有多數票就把剩下的圖掃完,回到相同輸入。

## small 不套分層

`SMALL_DOCX_THRESHOLD = 3`,small 最多 3 張圖,而且只掃佔頁面 7% 的 mol ROI
(實測 6 組設定 15.7 秒,無多數票退回 11 組約 45 秒),整份最壞 2.3 分鐘 ——
比分層後的 large(3 張 × 77 秒 = 3.9 分鐘)還便宜,不是瓶頸。

反而套下去有害:1~2 張圖的 docx 與 `{2,5,6}` 可能毫無交集,會被掃成零張,
產出一筆與「真的讀不到」無從分辨的全無命中。

**這批 21 份一份 small 都沒有**,所以上述時間是實測單張 ROI 耗時的推算,不是
整份 small 的實測。

## `classify_by_count` 必須吃原始張數

過去的碼是先過濾 `--image` 再 `classify_by_count(len(images))`。這是既有的
bug:`--image` 指定單張時 `len(images)==1` → 判成 small → 整份改走 mol-only。
分層會讓它更容易發生(5 張圖的 docx 第一層只剩 3 張)。現改為在任何過濾之前
用 `len(all_images)` 判定。

## 已知殘餘風險(明示接受)

`process_large_vs` 規則A 取 `mol_values ∩ permit_values` 的交集,而分層之後這個
交集**只由第一層三張圖的值組成**:

```
mol@image2 = "1234",image4 也印著 "1234",image5 多數票讀成 "1284"
全掃  permit_values = {1234, 1284} → 交集 {1234} → cross_match,採 1234
分層  permit_values = {1284}       → 交集空 → 衝突路徑,permit 優先,採 1284
```

這是唯一一條分層可能讓**最終值不同**的路徑,需三個條件同時成立。實測 21 份
所有 permit 值都只出現在 image5/6,一份都沒有。發生時 D 欄會寫「mol≠permit
衝突」並送 Vision,不是完全的黑箱,故接受。

要消除它得把「mol 與 permit 多數票對不上」也列為擴掃條件 —— 討論過,**決定不做**,
以換取邏輯單純。

## 逃生口

`--full-scan` 關掉分層,每張圖都掃。既是驗證工具(與全掃基準對帳),也是日後
版面改變、第一層失準時的退路。

## 實測結果

同一批 21 份,與全掃基準對帳:

```
全掃基準   134 張圖   10308 秒(2h51m)
分層        67 張圖    5564 秒(1h33m)   ← 省 46%

第一層 [2,5,6]:19/21 份一次命中,擴掃 2 份(32512、32545,本來就全無命中)

matches.csv 逐列(mol / id / final_value / status)  :21 份中 0 份有差異
build_vision_queue 分流(決定 B/C/D 欄)             :21 份中 0 份有差異
```

擴掃的兩份各多掃 4 張與 3 張,故是 60 + 7 = 67 張。

### 對帳時補的一個洞

`scan_tier` 欄第一次跑出來 21 份全是 1,擴掃過的兩份看不出來 —— 它們擴掃後仍
沒命中,寫進 CSV 的是 `_empty_result` 造的佔位列,用了預設值。而**「大量擴掃且
仍沒命中」正是分層規則過期最典型的表現**,偏偏就是這一格失真。佔位列改為在
擴掃過時標 2。
