# 名冊補充檔:自建仲介放獨立檔,不改官方名冊

[CONTEXT.md](../../CONTEXT.md) 把名冊定義為「許可證與仲介機構之間的唯一權威對照」,
而它的更新方式是**整份重新下載覆蓋** `data/agency_roster.json`。

於是直接手改那個檔的人會遇到一件事:下次更新名冊,手加的那筆消失,而且**沒有任何
訊號** —— 要等到下一批契約跑完、那家仲介的 E~G 欄又空了,才會發現。

地址那邊早就踩過同一個坑,解法是 `data/custom_roads.json`
([ADR-0001](0001-address-db-owns-tw-text-normalisation.md) 之後加的)。本 ADR 把
同一個模式套到名冊上。

## 做法

`data/custom_agencies.json` —— 一個 JSON 陣列,每筆的欄位名與官方名冊相同。
`fetch_roster()` 讀完官方檔後合併,所以 `PermitLookup` 與 `export_roster_xlsx`
兩個入口都自動吃到,不必各自處理。

一筆最小可用的記錄:

```json
[
  {
    "許可證":   "2340-2",
    "機構名稱": "某某人力仲介有限公司台北分公司",
    "機構地址": "臺北市中正區某某路1號5樓",
    "電話":     "02-12345678"
  }
]
```

**只有這四個欄位是必要的。** 官方記錄有 15 個欄位,但 pipeline 只用到這四個加上
兩個狀態欄,而狀態欄省略即可:`_is_active()` 讀不到 `終止營業日期` / `廢止許可日期`
時得到空字串,空字串就是「目前有效」。反查救援只採用有效的機構,所以**寫錯這兩欄
的後果是那筆建進了索引卻永遠不會被用到,且沒有錯誤訊息** —— 省略反而比填錯安全。

## 同許可證時自訂優先

會手動加一筆,正是因為官方那筆不合用:常見是新設分公司尚未收錄,或名稱、電話已
變更而名冊未更新。若讓官方蓋掉自訂,這個檔就沒有存在意義了。

比對用 `_parse_permit()` 的正規化結果,所以自訂寫 `"9001"` 蓋得掉官方的 `"09001"`
—— 前導零是名冊的書寫慣例,不是識別的一部分。反過來,`2340` 與 `2340-2` 是不同的
兩家(母公司與分公司),不會互相覆蓋。

## 壞掉就安靜跳過

補充檔缺失、不是陣列、JSON 語法錯 —— 一律原樣回傳官方名冊。這是個可有可無的
補丁,不該讓它擋掉權威資料。

代價是**格式壞掉時補充功能會默默失效**,沒有人會發現。故 `test_custom_agencies.py`
有一組 `TestShippedFileIsValid`,直接對版控裡那份檔案驗格式與必要欄位 —— 壞掉會在
測試裡亮,不必等到跑批次。

## 這不是繞過權威名冊

補充檔的正當用途是「官方確實還沒收錄」。**若某家查不到只是因為名冊過期
(`ROSTER_STALE_DAYS = 30`),正確做法是重新下載,不是手動加一筆。** 手動加的那筆
不會隨官方更新而修正,名稱或電話日後變更時會變成一個安靜的錯值 —— 與 ADR-0003
講的「填錯的格子人看不見」同一個性質。

新增之前先確認名冊日期,是這個機制唯一需要的紀律。
